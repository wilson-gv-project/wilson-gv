## What it is

`ResLocGeoObject` stores where a resonance sits in frequency space. It holds one value per spectral axis:
- A number (like `1864.0`) means the resonance is fixed at that frequency on that axis.
- `'all'` means that axis is free, so the resonance covers the whole axis.

Depending on how many axes are free, the object is a point (none free), a line (one free) or a plane (two free).

**Where it's made:**
- `solve_LSE_motif` in [evaluate.py:968](src/wilson_suite/wilson_intensities/refac_rsp_eval/evaluate.py#L968) (new code). Axes that no condition mentions get `'all'`.
- `solve_LSE_motif` in [resonances.py:125](src/wilson_suite/wilson_intensities/amplitudes/resonances.py#L125) (old code). It only ever makes points.

**Where it's used:**
- As a dictionary key, to group features by location: `dict[ResonanceMotif, dict[ResLocGeoObject, list]]`.
- As `SpectralFeature.location`, which drives the box around each feature, the window checks and the intensity calculation.

## Pros

- **Can be a dictionary key.** It supports hashing and `==`, so features at the same spot group together.
- **Axis order doesn't matter.** The coordinates are sorted, so `{'A':1,'B':2}` equals `{'B':2,'A':1}`.
- **Handles any number of dimensions.** Point, line and plane all use the same class.
- **Readable printout**, e.g. `Line(A=1864.0, B=all)`.
- **Small and simple**, with its own tests in `test_geoobject.py`.

## Cons and risks

**1. There are two copies of the class.**
- The two copies (in [plan.py:413](src/wilson_suite/wilson_intensities/refac_rsp_eval/plan.py#L413) and [spectrum_composition.py:201](src/wilson_suite/wilson_intensities/amplitudes/spectrum_composition.py#L201)) are identical today, but they are separate classes.
- The equality check (`__eq__`) first checks that the other object is the same class. So an object from one copy never equals one from the other copy, even with the same coordinates.
- Right now the new code makes objects from the `plan.py` copy, and the old code makes and compares them with the other copy. If the two paths ever meet, matching locations won't group and features will quietly not match.

**2. It isn't really read-only.**
- `_coord_dict` is the caller's own dict, not a copy. If the caller changes that dict later, `_coord_dict` changes but `coordinates` and the hash don't. The two then disagree.
- `coordinates` is a normal attribute that anyone can reassign. For something used as a dictionary key, that's unsafe.

**3. Callers reach into its private data.**
- `location._coord_dict[...]` is read directly in about 6 places in `spectrum_composition.py` and in tests.
- There is no public way to "give me the value on axis A as a number", although `loc['A']` exists.

**4. `'all'` breaks the point-only code.**
- `contains_feature`, `contributing_feature` and the box code compare values with `>=`. With `'all'` they crash (Python can't compare text with a number).
- The new solver can now produce lines, so this crash can actually happen.

**5. Exact float matching.**
- Locations come from a least-squares solver (`lstsq`). Tiny rounding noise, like `1864.0` vs `1864.0000000002`, gives two different dictionary keys. Resonances that should group together won't.

**6. It can only describe lines and planes that run straight along the axes.**
- A diagonal resonance like `w_A + w_B = b` can't be stored. There's already a FIXME for this at [evaluate.py:959](src/wilson_suite/wilson_intensities/refac_rsp_eval/evaluate.py#L959).

**7. Smaller issues:**
- `features_in_bounds` calls `location.as_array()`, which doesn't exist ([spectrum_composition.py:810](src/wilson_suite/wilson_intensities/amplitudes/spectrum_composition.py#L810)). The code is marked unused, but it would crash if called.
- `dims` is marked "UNUSED", but it is used at [spectrum_composition.py:504](src/wilson_suite/wilson_intensities/amplitudes/spectrum_composition.py#L504), where `N = len(dims)` counts free axes too. Check whether a line feature should count them.
- There's no input check: an empty dict, `NaN`, `'All'` or other text are all accepted.
- There's no sort order, so you can't sort features by location to get a stable order.
- The printout says "Object" for 3+ free axes, and "Point()" for an empty location.
- `find_clusters_by_distance` uses `location.values` as a key. That drops the axis names, so order depends on sorting.

## Suggestions (in order of value)

1. **Keep a single copy.** Keep it in one module (probably `plan.py`, since the refactor is heading there). The other module should just import it.
2. **Make it a frozen dataclass** (a data class whose fields can't be changed after creation):
   - Store only `coordinates` (the sorted tuple).
   - Copy the input dict when the object is made.
   - Drop `_coord_dict`, or make it a read-only view.
3. **Add public helpers** so callers stop using `_coord_dict`:
   - `fixed_axes()` / `free_axes()`
   - `as_dict()`
   - `as_array(axes)` (this also fixes the missing method)
   - `value(axis) -> float` that fails clearly on `'all'`
4. **Round when creating the object.** Something like `round(v, 6)`, or snap to a set tolerance, so solver noise doesn't split keys.
5. **Check inputs.** Refuse an empty dict and `NaN`, and allow only a number or the free marker.
6. **Replace the `'all'` string** with a dedicated marker (e.g. `FREE = ...` or an enum). This avoids typos and makes type checks stricter.
7. **Make the window and box code handle free axes.** A free axis always "overlaps" the window. Or have those functions clearly say "points only".
8. **Add `__lt__`** (sort by axis values) so feature order is stable.

## Future potential

- **Diagonal resonances.** Store a general flat shape: one base point plus direction vectors (an "affine subspace"). That fixes the FIXME and supports conditions like `w_A + w_B = b`. The current axis-aligned form becomes a special case.
- **Geometry operations:**
  - `intersect(other)`: where two resonances meet (e.g. a line crossing a point).
  - `contains(point)`: does this point lie on the line or plane?
  - `distance(point)`: useful for clustering and for deciding if a feature contributes to a window.
  - `project(axes)`: look at a 2D location in 1D, e.g. for slices of a 2D spectrum.
- **Drawing.** `dimensionality` could decide what to draw: a marker, a line or a band.
- **Caching.** Now that the new `solve_LSE_motif` takes `axes`, stored locations could be reused across runs as long as their keys are stable (points 4 and 6 above).
